PROMPT 01
----------------------------------------------------------------------
I have a new project. I have create a decision document that I want you to
use as a guidance. Don't act on it yet, but this will be guidance for what we
will build:

Data shape: Relational. My app has a shared card catalog that every user draws
from, a collection of the copies each user owns, and trades that move copies
between two users. Those are clean links between separate things, which is
relational by nature. A document model would copy each card's player and set
details into every user's collection, so fixing a mistake or answering "who
owns this card?" would get messy. Tradeoff: I have to settle the structure up
front, including how the catalog and collections split and how parallels,
autographs and serial-numbered cards are represented. If I get that wrong,
reshaping the tables once real users have built collections is real work.

Database: Postgres. Once the data is relational, Postgres follows. Row-level
security keeps each user's collection private, and a JSONB column can hold
unusual card attributes without breaking the structure. SQLite struggles with
many people writing at once, and that's exactly what a multi-user app does.
Tradeoff: Every schema change, like adding grading companies or trade tables,
is a migration I have to write, test and run against live data. That upkeep
is mine.

Backend language: TypeScript (Node). One language runs across the web app, the
API and the React Native mobile app. The phone and server can share the same
definitions for a Card or a Trade, so they can't drift apart. Python on the
backend would split the project into two languages. Tradeoff: Node is poor at
heavy computation. If I tried to run card-image recognition myself, I'd need a
separate worker in another language. Right now that's a call to an outside
service, so the cost is acceptable, but the limit is real.

Backend framework: Next.js. The web pages and the API that my mobile app calls
live in one project with one deploy. With Express, I'd build and run the
backend as a separate second project. Tradeoff: Next.js is designed mainly for
websites, and it dictates how my routes, caching and rendering work. My mobile
app's API inherits those rules, and leaving Next.js later would mean rewriting
the API layer, not just moving it.

Frontend: React (via Next.js). React on the web carries over directly to React
Native on mobile, so I learn one way of building screens and use it on both.
Vue or Svelte wouldn't give me that path to the phone. Tradeoff: I'm using
Next.js's version of React, with its split between server and client
components and its rules for loading data. The web frontend can't change
direction unless the backend framework changes with it.

Hosting: Vercel. This is the last row because it's the easiest to change. My
backend handles short requests: API calls from the phone, page loads and a
nightly price-update job. That fits Vercel's model better than an always-on
server on Render. Tradeoff: Vercel's functions start and stop with each
request instead of staying running, so they can't hold long-lived Postgres
connections. I need a connection pooler, and a continuous background job like
price scraping wouldn't fit here. That job would have to run on another host
such as Render.

What it gives you:
This sets the ground rules for the whole project without building anything.
The decision document fixes the stack (relational data in Postgres,
TypeScript, Next.js for both pages and API, React, Vercel hosting) and, just
as important, records the tradeoff you accepted for each choice. Claude saved
it as standing guidance, so later work is checked against it, and replied
with a few early warnings: Vercel no longer offers its own Postgres (Neon via
the Marketplace is the usual route), row-level security needs the user's
identity passed to Postgres on every request, and the catalog/copy structure
is the riskiest design decision to get right.

PROMPT 46
Set up structured logging with levels (debug, info, warn, error). Each line should be JSON with a timestamp, level, an event name, and an optional details object. Read the active log level from an environment variable so I can make prod quieter than dev.

What it gives you:
A small, dependency-free logger in lib/log.ts. Call log.debug/info/warn/error("event.name", { ...details }) and it writes one JSON line ({"ts","level","event","details"}). The LOG_LEVEL environment variable (debug, info, warn or error) sets the lowest level that gets written. If it isn't set, dev shows everything and production starts at info, so prod is quieter by default. Errors put in details keep their message, code and stack instead of turning into {}, and warn/error lines go to stderr so Vercel's log viewer marks them. The health check route now uses it, and LOG_LEVEL is documented in .env.example.
